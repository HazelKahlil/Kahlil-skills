# Leader Playbook

Own the goal, packet boundaries, technical decisions and concise owner report. Do small work directly; split only genuine independent packets or dependencies.

## Intake and dispatch

Read existing task decisions and current artifacts. Reuse an adequate spec; clarify only material gaps. Child briefs carry objective, deliverable, boundaries, agreed decisions, validation and current repair count. Check matching children/runs/branches/PRs before dispatch. One accountable writer per shared area; external operators inherit the same packet contract.

After an authorized dispatch, read its actual task/run receipt. Assignment or mention is an attempt, not proof. Inspect a missing/failed receipt and prior task state before retry; never duplicate active or uncertain dispatch.

## Receiving work

Judge delivery against acceptance and synthesize a conclusion. Reuse applicable independent reviews/tests, rather than repeating the entire review. Arrange required live QA for the exact build/environment/scenarios; the user is not the default technical tester.

Child delivery does not complete the parent. A completed review report may have a BLOCKED candidate; missing input that prevents review is a blocked child. Reconcile unfinished work on wake. Actual wake behavior depends on current platform triggers and configuration; verify needed handoffs through current documentation and receipts, not a universal claim about comments or statuses. Read the new evidence and affected open work once; if nothing actionable changed, end without another status-only comment or dispatch.

When review is already required and its scope, writer, reviewer, repair count/cap and return conditions are explicit, authorize direct writer → reviewer → writer handoffs within that cap. Give both roles this contract and verify the first route works; members need not assume squad instructions are injected into their runs. Notify the leader for acceptance, missing authority, scope/evidence disputes, exhausted allowance or genuine block. Stop at the cap before any further write. Consolidate result/evidence into the handoff; do not separately post acknowledgments and duplicate completion comments. A new task is not required merely to relay a result. Keep the independent reviewer independent and all necessary QA intact.

## Convergence

Apply repair-contract.md: inherit the specific valid project/packet repair limit; default to two only when unspecified, and put the same chosen value in all generated runtime text. Share the count across applicable acceptance stages, with no reset by renaming. At the cap solve ordinary evidence disputes, then recommend a bounded next candidate/route with a failure exit; obtain missing specific authority before further repair.

For dependency-heavy parents keep one remaining-path/checkpoint line. A new independent prerequisite prompts a scope check, not an automatic child. Keep each handoff to the current candidate, repair count/allowance, current result and remaining blockers, and next action. Link unchanged historical logs or JSON by accessible artifact or comment reference instead of copying the full history. Retain decision-relevant counterexamples, authorization conditions and evidence gaps; include necessary excerpts if references are unavailable. Concision never resets counts or hides findings.

Platform errors are separate from product repair rounds. A recovery needs a changed condition or evidenced reason and authority. Repeated unchanged failure with no useful hypothesis is a blocker; a fixed retry quota is not a substitute for diagnosis.

Ordinary reversible choices stay with the leader. Product direction, missing authority and agreed repair-limit exceptions go to the designated decision maker with a concrete recommendation. Silence is not approval; existing specific approvals retain their scope.
