# Repair and Acceptance Contract

Generate a self-contained common runtime contract. Roles without this Skill attached must receive the applicable rules in their squad/role/brief; a reference to this file alone is insufficient.

## Bounded packet and count

A packet has an agreed result, acceptance and scope. A multi-goal parent is not one repair allowance; renaming unfinished work is not a new allowance. The leader records boundaries in the existing issue, without a new ledger.

Use the current specific, valid project/packet decision for the autonomous repair limit; only when none is specified, default to two substantive repair deliveries. Resolve the chosen limit once and write the same value into the common instructions, applicable roles and handoffs; do not require runtime roles to retrieve this designer-only reference. Initial self-tested candidate is R0; revisions are numbered R1, R2, and so on without resetting. Code review, applicable live QA and contract-related user findings before final acceptance share the count. Partial PASS, agents, models, PRs, tasks and chats do not reset it.

Edits, commits, builds and tests before re-delivery are not separate rounds. A delivered repair candidate that cannot build still uses its opportunity. Same-candidate evidence clarification is not a repair; actual implementation/configuration corrections cannot be relabeled as evidence. Repeated failed preparation without a useful new hypothesis or evidence must stop. The allowance is a ceiling, not a target: accepted work ends immediately; repeated ineffective changes may stop earlier. Optional wording/style/refactoring preferences outside acceptance are nonblocking suggestions, not repair assignments. Mandatory tests and real defects remain required.

Missing environment/login is a validation gap, not automatically a repair. A delivered environment/configuration that fails its agreed contract may require a counted correction. Genuine new requirements get recorded scope; relevant old defects and spent effort remain. A new defect after true completed acceptance may get a linked new packet; never close before required acceptance to reset the allowance.

## Recheck and exit

Disclose all currently evidenced relevant blockers together, with trigger, impact, evidence and clearance. Top-three means summary, not a finding cap. Recheck original counterexamples and affected paths; a newly discovered serious relevant defect, including a missed existing one, may block without reopening unrelated work or resetting rounds.

At the packet's established autonomous repair limit, finish the current candidate's remaining necessary validation. If further substantive modification is needed, stop autonomous patches and repeated dispatch. The leader resolves ordinary evidence disputes within authority and presents the remaining counterexample, recommended route, next check and failure exit. Extra repair requires a specific user decision or explicitly delegated authority; an existing specific approval remains valid. Continue with the next R number; do not reset the count or silently raise the limit. Silence or general encouragement is not unlimited repair authority. Where a valid project policy delegates one conditional extension to the leader, include the same eligibility, maximum total revisions and failure exit in every applicable role and brief. It needs a recorded concrete remaining defect, a new evidence-backed corrective approach, in-scope change and next check; do not chain the same delegation into another extension. No such project delegation means no assumed extra allowance. Preserve stricter packet decisions and existing freezes.

Keep unresolved candidates failed, state the responsible decision maker and recovery trigger, and do not pretend background continuation. Independent authorized work can continue; a cap does not complete the user's goal or lift an existing freeze.

## Dependencies and QA

For dependency-heavy parents only, keep one current line: remaining path → next verifiable result → reconsideration condition. Removing a real prerequisite can be progress before the final UI case runs. New independent engineering or material scope/cost changes need a route comparison before adding work. Ordinary reversible choices within authority stay with the leader.

Use validation appropriate to behavior risk and the project contract. Agents complete applicable engineering/live QA before user product acceptance. A handoff carries exact candidate, scenarios, valid evidence and gaps to a known recipient; a brief is not proof QA ran. Docs-only changes do not need app installation. Reuse evidence only while candidate, environment, dependencies and affected behavior remain applicable.

Child delivery, review verdict, parent acceptance and installed/deployed/published state are distinct. Report only applicable stages; no mandatory multi-column form for every comment.
