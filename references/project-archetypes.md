# Project Archetypes

## New project

Goal: establish clean operating rules before code volume grows.

Start with roles, Definition of Done, RFC expectations, CI/test commands, PR policy, and Project Resources.

## Existing project

Goal: respect existing conventions before agents act.

First discover repo structure, existing tests, CI, coding standards, release process, and ownership boundaries. Do not let Worker make broad changes until the map is accepted.

## Legacy migration

Goal: prevent backlog avalanche.

Old issues stay in Backlog. Audit first, classify by lane, create a batch plan, pilot 3–5 low-risk issues, then expand.

## Takeover / handoff

Goal: understand risk before changing code.

Create a handoff map: owners, repos, active incidents, risk areas, deployment process, test coverage, secrets, stale docs, and urgent decisions.

## Temporary project / spike

Goal: maximize learning while limiting blast radius.

Define timebox, output artifact, allowed scope, exit criteria, cleanup/archival plan, and whether code is disposable.

## Incident / maintenance

Goal: restore health safely.

Prioritize reproduction, impact, mitigation, rollback, fix, validation, and postmortem. Avoid speculative rewrites during incident response.

## Multi-repo project

Goal: avoid repo confusion.

List each repo/service, branch, ownership, deployment boundary, and issue lane. Attach Project Resources wherever possible.
